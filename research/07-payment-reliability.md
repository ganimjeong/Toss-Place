# 결제 요청의 신뢰성: 멱등 키, 결과 모름, 조회

결제 SDK(`packages/payment-sdk`)를 설계하기 전에 PG와 POS 결제 연동 문서가 "응답을 못 받은 결제"를 어떻게 다루는지 조사함.

## 토스페이먼츠 멱등 키 [공개]

- `Idempotency-Key` 헤더로 보냄. UUID처럼 충분히 무작위한 값을 쓰고 최대 300자
- 처음 요청한 날부터 15일간 유효함
- 이미 처리된 요청을 같은 키로 다시 보내면 다시 처리하지 않고 첫 응답을 그대로 돌려줌
- 같은 키의 이전 요청이 아직 처리 중이면 `409 IDEMPOTENT_REQUEST_PROCESSING`. 다시 요청해서 응답을 확인하라고 안내함
- 멱등 요청이 에러를 돌려줬을 때 "멱등키를 변경해서 동일한 요청을 재시도하는 것은 위험"하다고 경고하고, 원인을 먼저 확인하라고 함

이 레포에 가져온 것

- 응답을 못 받은 결제를 새 키로 다시 보내지 않음. 같은 키로 조회해서 결과를 확정함
- "처리 중" 응답이 따로 있다는 점. 조회 결과를 `approved`, `not-found`, `processing` 셋으로 나눈 근거임

## Adyen POS 타임아웃 가이드 [공개]

단말기 결제의 타임아웃을 종류별로 나눠서 안내함.

- 처리 타임아웃: 결과가 실패로 돌아오지만, 연동 쪽에서 거래 상태 조회(transaction status request)를 자동으로 보내 실제로 처리됐는지 확인하라고 함
- 요청 타임아웃: 단말기가 아직 손님 입력을 기다리는 중일 수 있고, 손님이 결제를 끝낼 수도 있다고 명시함. 역시 상태 조회로 진행 중인지 끝났는지 확인하라고 함
- 기기 타임아웃(손님이 카드를 안 댐): 명확한 취소라서 다시 결제해도 됨

이 레포에 가져온 것

- 실패 사유를 "확정 실패"와 "결과 모름"으로 나눔. 나누는 기준은 번들이 `isAmbiguous`로 정함
- 결과 모름이면 결제 요청이 아니라 조회를 자동으로 반복함

## 국내 VAN 망취소 [추정]

국내 카드 단말기 연동에서는 승인 응답을 받지 못하면 같은 거래를 취소 전문으로 보내는 망취소를 쓴다고 알려져 있음. 공개 규격서를 찾지 못해서 구현에는 넣지 않음.
`not-found`로 확정한 뒤 늦게 도착한 원래 요청이 승인되는 경우는 지금 구조로 막지 못함. 실제 단말기를 붙이면 `not-found` 확정 전에 그 멱등 키로 망취소를 보내는 방식을 검토해야 함.

## 정리

| 질문                         | 이 레포의 답                                                     |
| ---------------------------- | ---------------------------------------------------------------- |
| 자동 재시도는 무엇을 하나    | 조회만 함. 조회는 읽기라 여러 번 해도 안전함                     |
| 결제 요청 자체는 다시 보내나 | 자동으로는 안 보냄. 사장님이 다시 누르면 먼저 이전 시도를 조회함 |
| 응답 전에 앱이 꺼지면        | 요청 전에 저널에 기록하고 다음 실행 때 조회함                    |
| 조회도 계속 실패하면         | `unknown`으로 남기고 같은 주문의 새 결제를 막음                  |

- Adyen POS timeouts https://docs.adyen.com/point-of-sale/error-scenarios/pos-timeouts
