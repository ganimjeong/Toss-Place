# 좋은 코드의 기준 (Frontend Fundamentals)

토스가 공개한 "변경하기 쉬운 프론트엔드 코드를 위한 지침서". 이 레포의 리뷰 기준으로 씀. [공개]

## 1. 가독성

맥락 줄이기

- 같이 실행되지 않는 코드 분리하기. 예: 보기 권한과 관리자 권한 분기를 한 컴포넌트에 섞지 않음
- 구현 상세 추상화하기. 예: 로그인 확인 로직을 감싸는 컴포넌트로 빼기
- 로직 종류에 따라 합쳐진 함수 쪼개기. 예: 쿼리 파라미터 전부를 다루는 큰 훅 대신 파라미터별 훅

이름 붙이기

- 복잡한 조건에 이름 붙이기
- 매직 넘버에 이름 붙이기

위에서 아래로 읽히게 하기

- 시점 이동 줄이기
- 삼항 연산자 단순하게 하기
- 왼쪽에서 오른쪽으로 읽히게 하기. 예: `a <= x && x <= b`

## 2. 예측 가능성

- 이름 겹치지 않게 관리하기. 예: 라이브러리와 같은 이름의 래퍼를 만들지 않음
- 같은 종류의 함수는 반환 타입 통일하기
- 숨은 로직 드러내기. 함수 이름과 파라미터, 반환값만 보고 동작을 예측할 수 있어야 함

## 3. 응집도

- 함께 수정되는 파일을 같은 디렉토리에 두기
- 매직 넘버 없애기. 관련된 값이 여러 곳에 흩어지지 않게 함
- 폼의 응집도 생각하기. 필드 단위와 폼 전체 단위 중 변경 단위에 맞는 쪽을 고름

## 4. 결합도

- 책임을 하나씩 관리하기
- 중복 코드 허용하기. 섣부른 공통화가 결합도를 높일 수 있음
- Props Drilling 지우기. 컴포넌트 조합을 먼저 쓰고, 그다음 Context

## 네 기준 사이의 균형

- 응집도를 높이려고 추상화하면 가독성이 떨어질 수 있음
- 중복을 허용하면 결합도는 낮아지지만 응집도는 떨어질 수 있음
- 함께 바뀌지 않으면 위험한 코드라면 응집도를, 그렇지 않으면 가독성을 우선함

## 접근성

Frontend Fundamentals 접근성 섹션의 주요 원칙 [공개]

- 올바른 구조
- 명확한 의미
- 예측 가능한 인터랙션
- 시각 정보 보완
- eslint로 접근성 문제를 작성 단계에서 잡고 디자인 시스템과 결합함

## 이 레포에 반영한 것

- 린트로 강제: 중첩 삼항 금지, `any`와 타입 단언 금지, 엄격한 비교, 접근성 규칙
- 도메인 폴더 단위 배치: `bundles/order/src/order/{apis,components,hooks}`
- 같은 종류 함수의 반환 통일: 기기 호출은 모두 `BridgeResult` 반환
- 매직 넘버 이름 붙이기: `FAKE_NETWORK_DELAY_MS`, `SKELETON_COUNT`
