# 시재관리 번들 회고

두 번째 웹뷰 번들. 마감할 때 권종별로 현금을 세서 있어야 할 현금과의 과부족을 보여주고, 금전함을 여는 기능.

## 한 줄 요약

두 번째 번들을 만들면서 첫 번들 구조가 복사해서 쓸 만한지 확인했다. 대부분 그대로 옮겨졌고, 옮기면서 중복을 남길지 공통화할지 기준이 필요했다.

## 1. Object.fromEntries가 키 타입을 잃어버림

- 이슈: 권종별 0장으로 초기화하는 객체를 `Object.fromEntries(DENOMINATIONS.map(...))`로 만들었더니 타입이 `{ [k: string]: number }`가 됨. `as CashCount`로 맞추려 했는데 린트(`consistent-type-assertions`)가 막음
- 판단: 단언을 쓰면 권종을 추가하고 초기값을 빠뜨려도 컴파일러가 모름
- 해결: 8개 권종을 객체 리터럴로 직접 씀. 권종이 늘어나면 `Record<Denomination, number>` 타입 검사가 빠진 키를 알려줌
- 배운 점: 짧은 코드보다 컴파일러가 검증할 수 있는 코드가 낫다. 린트 규칙이 이 판단을 강제해줌

## 2. Providers를 공통 패키지로 올릴까

- 고민: 주문 번들의 `Providers.tsx`를 그대로 복사함. 바로 패키지로 올리고 싶었음
- 판단: 지금은 두 번들의 Providers가 같지만 바뀌는 이유가 다를 수 있음. 예를 들어 결제 번들만 결제 에러 리포팅을 붙일 수 있음. 번들은 독립적으로 배포되는 단위라 공통 패키지를 바꾸면 모든 번들을 다시 배포해야 함
- 결정: 중복을 허용함. 세 번째 번들에서도 같은 모양이면 그때 올림
- 배운 점: Frontend Fundamentals의 "중복 코드 허용하기"는 배포 단위가 나뉜 구조에서 특히 중요하다

## 3. 과부족 표시

- 결정: 금액이 맞으면 "딱 맞아요"를 초록색으로, 아니면 부호를 붙인 금액을 빨간색으로 표시함. 마감 때 사장님이 숫자를 계산하지 않고 바로 알 수 있게 함
- 장수 입력은 `inputMode="numeric"`으로 숫자 키패드를 띄우고, 숫자가 아닌 글자는 버림

## 테스트

- 권종별 장수를 입력하면 과부족이 0이 되는지, 숫자가 아닌 입력을 무시하는지, 금전함 연결이 끊기면 안내가 나오는지 확인함
