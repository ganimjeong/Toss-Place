## #6 결제 SDK

잘한 것

- 추상적인 "중복 결제 방지"가 아니라 레포 안의 실제 버그(멱등 키를 `useRef`에 둬서 번들 전환 때 사라짐)에서 출발함. 문제를 재현할 수 있어서 설계 판단마다 "이걸로 그 버그가 막히나"를 물을 수 있었음
- 테스트가 처음부터 다 통과한 걸 의심하고 보장을 하나씩 깨봄. 저널을 덮어쓰는 진짜 버그가 거기서 나옴

아쉬운 것

- PR이 너무 컸음. SDK 패키지, 브릿지 조회 API, 주문 번들 적용, 배포 워크플로가 한 PR에 들어감. 리뷰어가 상태 머신을 보다가 React Query 연결과 npm 배포 설정까지 같이 봐야 함. 브릿지 API, SDK, 번들 적용, 배포를 각각 PR로 나눌 수 있었음. 모두 앞의 것에만 의존해서 순서대로 쌓기도 쉬웠음
- 보장 목록을 테스트보다 늦게 만듦. "이 SDK가 지키는 것"을 먼저 적었다면 빠진 테스트(결과를 모르는 상태에서 다시 누르기)를 깨보기 전에 찾았을 것
- 남은 고민인 "결과를 모르는 동안 장바구니 잠그기"는 이중 결제와 같은 무게의 문제인데 다음으로 미뤄둠
- npm 배포는 워크플로와 tarball 검사까지만 했고 실제 배포는 못 함. scope가 정해지지 않았음

다음에는

- PR을 열기 전에 "리뷰어가 한 번에 머릿속에 들고 있어야 하는 것"이 하나인지 봄. 둘 이상이면 나눔
- 보장 목록 → 테스트 → 구현 순서로 함

## #7 셸 패키징

잘한 것

- "빌드 성공은 실행 성공이 아니다"를 문장으로 남기는 데서 끝내지 않고 CI 단계(스모크 테스트)로 만듦. 이후 #8에서도 Sentry 코드가 패키징된 앱을 깨지 않는다는 걸 이 단계가 자동으로 확인해줌
- 릴리스 워크플로를 PR에서도 돌게 해서 문제 세 개를 머지 전에 잡음

아쉬운 것

- 릴리스 워크플로가 두 번 실패함. 셋 다 로컬 검증의 빈틈이었음
  - 이전 빌드 결과(dist)가 남은 상태에서 빌드해서 빌드 순서 문제를 못 봄
  - Windows를 한 번도 돌리지 않고 Windows 경로 버그를 고쳤다고 판단함. 그 테스트가 Windows에서 깨짐
- devDependencies 선언으로 빌드 순서가 해결됐다고 회고 초안에 먼저 써버림. 도구가 그 선언을 어떻게 쓰는지(`-t`는 devDependencies를 안 봄) 확인하기 전이었음. CI가 반박해서 고침
- PR을 열 때 Windows 확인 항목을 체크하지 않은 채로 올림. 확인 안 된 걸 표시한 건 맞았지만, 리뷰 요청과 검증이 동시에 시작됨. 초안(draft) PR로 올려 CI를 먼저 통과시키고 리뷰 요청으로 바꾸는 게 맞았음

다음에는

- 빌드 산출물에 기대는 변경은 산출물을 모두 지운 상태에서 한 번 돌림
- 크로스 플랫폼 코드는 고친 플랫폼에서 돌려보기 전에 "고쳤다"고 쓰지 않음
- 회고의 결론은 검증 뒤에 씀

## #8 Sentry

잘한 것

- CSP가 리포팅을 막을 거라는 가설을 세우고, 가짜 수집 서버로 막히는 경우와 통과하는 경우를 둘 다 재현함. "아마 막힐 것"이 아니라 콘솔 메시지와 수집 서버 로그로 확인함
- 네이티브 크래시까지 같은 방식으로 끝까지 보냄
- 실제로 확인한 범위(가짜 서버)와 못 한 범위(실제 Sentry 프로젝트의 CORS 응답)를 PR과 회고에 나눠 적음

아쉬운 것

- Sentry API를 기억으로 썼다가 `sendDefaultPii` 타입 에러를 만남. 수집 범위 기본값이 바뀐 메이저 버전이었는데, 타입 에러가 아니었으면 모르고 지나갔을 수도 있음. 개인정보 관련 옵션은 설치한 버전 문서부터 봐야 했음
- 번들 크기가 gzip으로 31KB 늘었는데 판단을 미룸. 측정은 했으니 기준(예: 셸 실행 후 첫 화면까지 시간)을 정하고 결정해야 함
- #6, #7을 합친 브랜치 위에 쌓아서 PR diff가 처음에 1200줄로 보였음. 본문에 안내는 했지만 리뷰하기 어려운 모양이었음

## 머지 과정

- 이슈: #6을 squash 머지하자 #7이, #7을 머지하자 #8이 충돌함. #8은 파일 9개가 충돌함
- 원인: squash 머지는 브랜치의 커밋들을 새 커밋 하나로 만듦. #8 브랜치에는 #6, #7의 원래 커밋이 있고 main에는 같은 내용의 squash 커밋이 있어서, git은 같은 변경을 서로 다른 두 변경으로 봄
- 해결: 내용은 #8 브랜치가 #6, #7을 모두 포함한 상위 집합이라 충돌 파일은 #8 쪽을 택함. 그다음 main 대비 diff에 Sentry 파일만 남는지 확인하고, lockfile은 `yarn install --immutable`로, 나머지는 깨끗한 상태의 전체 검사와 CI(OS별 패키징 포함)로 확인한 뒤 머지함
- 배운 점: squash 머지 레포에서 PR을 쌓으려면 처음부터 앞 PR 브랜치를 base로 두는 게 맞음. 앞 PR이 머지되면 GitHub이 base를 main으로 바꿔주고, 남은 PR은 `git rebase --onto main <앞 브랜치>`로 자기 커밋만 옮기면 됨. 이번처럼 두 브랜치를 merge해서 쌓으면 충돌을 "어느 쪽이 상위 집합인가"로 판단해야 하고, 그 판단을 diff로 따로 검증해야 함
