# 영업시간 내내 켜 두는 포스의 성능 회고

셸 빌드 결과를 Electron으로 띄우고 Chrome DevTools Protocol로 첫 화면, 입력 반응, 결제 수백 건 뒤의 메모리를 재는 스크립트(`apps/shell/scripts/measure.ts`)를 만들고, 거기서 나온 누수 두 개를 고친 작업.

## 한 줄 요약

화면 속도는 저사양 조건에서도 여유가 있었고, 문제는 오래 켜 둘 때 쌓이는 쪽에 있었다. 닫힌 다이얼로그는 화면에 그려지지 않아서 DOM으로는 안 보였고, GC 뒤 힙과 힙 스냅샷 비교로만 드러났다.

## 측정 조건

- 매장 단말기는 개발 PC보다 느려서 CPU 스로틀링 1배, 4배, 6배로 잼. 번들은 로컬 파일이라 네트워크보다 파싱과 실행 비용을 봄
- 첫 화면은 번들로 이동한 뒤 `#root`가 처음 그려진 시점, 스크립트 실행 시간(`Performance.getMetrics`의 ScriptDuration), 50ms 넘는 long task의 초과분 합. 각 조건 7회 중앙값
- 입력 반응은 클릭의 `event.timeStamp`부터 바뀐 화면이 그려진 다음 프레임까지
- 장시간 운영은 메뉴 담기, 카드 결제, 결과 다이얼로그 확인을 300번 반복하면서 50건마다 GC 후 힙과 DOM 노드 수를 잼. 측정할 때만 단말기 승인 지연을 3초에서 50ms로 줄임(`POS_STUB_CARD_DELAY_MS`)
- 근거와 지표 선택 이유는 [research/09](../research/09-pos-performance.md)

## 1. 첫 화면과 입력 반응은 여유가 있었음

| 조건 | 주문 번들 첫 화면 | 스크립트 실행 | long task 초과분 | 메뉴 누름 반응 p75 |
| ---- | ----------------- | ------------- | ---------------- | ------------------ |
| 1배  | 16.1ms            | 7.5ms         | 0ms              | 14.0ms             |
| 4배  | 47.1ms            | 27.2ms        | 0ms              | 12.9ms             |
| 6배  | 70.2ms            | 38.8ms        | 0ms              | 14.0ms             |

- 메뉴가 보이기까지 약 350ms 중 300ms는 서버 대신 넣어 둔 가짜 지연(`FAKE_NETWORK_DELAY_MS`)임. 서버가 붙으면 이 구간은 데이터 패칭 문제가 됨
- 결론: 지금 크기에서는 첫 화면을 줄이려고 구조를 바꿀 이유가 없음. 번들이 커질 때 비교할 기준값으로 남김

## 2. 결제마다 닫힌 다이얼로그가 쌓임

- 이슈: 결제 300건 동안 GC 뒤 힙이 2.3MB에서 4.0MB로 늘었고 줄지 않음. DOM 노드 수는 84로 그대로라 화면만 봐서는 알 수 없음
- 원인 찾기: 결과 다이얼로그를 `overlay.open`으로 띄우고 확인 버튼에 `close`만 연결했음. overlay-kit 1.9.0의 리듀서를 읽어 보니 `CLOSE`는 `isOpen`만 false로 바꾸고 오버레이를 목록에 남김. 지우는 건 `REMOVE`(`unmount`)뿐. 닫힌 `ResultDialog`는 `null`을 그려서 DOM에는 없지만 컴포넌트와 클로저는 마운트된 채 남고, 다이얼로그를 열 때마다 쌓인 목록 전체가 다시 렌더됨
- 해결: 결과 다이얼로그는 확인에 `unmount`, 영수증 출력 실패 다이얼로그는 `close(답)`으로 응답을 돌려준 뒤 `unmount`
- 확인

| 결제 건수 | 수정 전 힙 | 수정 후 힙 |
| --------- | ---------- | ---------- |
| 0         | 2.3MB      | 2.3MB      |
| 300       | 4.0MB      | 3.5MB      |

- 6배 스로틀에서 같은 반복을 한 번씩 돌리면, 수정 전에는 결제가 쌓일수록 누름 반응 p75가 19.3ms에서 22.6ms로 계속 올랐고 수정 후에는 17.8~24.1ms 사이에서 오르내림. 한 번씩만 돌려서 경향으로만 봄
- 재발 방지: 결제를 세 번 반복한 뒤 `useOverlayData()`로 오버레이 목록이 비었는지 보는 테스트 두 개. 수정 전 코드로 되돌리면 둘 다 실패하는 것을 확인함. 닫힌 다이얼로그는 DOM에 없어서 `queryByRole`로는 이 문제를 잡을 수 없음
- 배운 점: 화면에서 사라진 것과 메모리에서 사라진 것은 다르다. 라이브러리의 닫기가 무엇을 지우는지는 문서 예제(`onExit={unmount}`)보다 리듀서를 읽는 게 확실했다

## 3. 남은 증가분은 무엇이었나

- 수정 뒤에도 300건에 1.2MB가 늘어서, 결제 200건 전후로 힙 스냅샷을 떠서 이름별 개수와 크기를 비교함
- 가장 큰 건 V8이 반복 실행된 코드를 최적화 컴파일한 결과(InstructionStream 등 약 360KB)와 Chromium이 클릭마다 쌓는 성능 타임라인 기록(PerformanceEventTiming, LargestContentfulPaint, SoftNavigationContext 등)
- 앱 객체로는 압축된 이름 `Tf` 200개가 있었고, 번들에서 찾아보니 TanStack Query의 `Mutation`. 결제 mutation마다 하나씩 생겨 gcTime(기본 5분) 동안 남음. 결제 뒤 6분을 기다렸다가 다시 재니 0.1MB가 풀림
- 결론: 남은 증가분은 엔진 쪽 기록과 시간이 지나면 풀리는 캐시라 앱에서 고칠 대상이 아님. 다만 Chromium 성능 타임라인이 실제 단말기에서 하루 동안 어디까지 커지는지는 기기에서 확인해야 함

## 4. 결제 SDK가 확정된 주문 상태를 계속 들고 있었음

- 이슈: `createPaymentClient`의 `states` Map이 주문마다 마지막 상태(승인 정보 포함)를 지우지 않음. 포스를 켜 둔 동안 결제 수만큼 늘어남
- 판단: 상태 전이 표를 다시 보니 `approved`, `failed`는 `REQUEST`만 받고 `idle`도 `REQUEST`를 받음. 확정 상태를 지워서 `idle`이 돼도 다음 결제 흐름은 똑같음. 반대로 `requesting`, `reconciling`, `unknown`은 이전 시도를 지켜야 하므로 지우면 안 됨
- 해결: 확정 상태는 확정된 순서대로 최근 `settledStateLimit`(기본 50)건만 남기고 오래된 것부터 지움. 진행 중이거나 결과를 모르는 상태는 지우지 않음
- 재발 방지: 상한을 넘으면 오래된 확정 상태가 지워지는지, 확정 주문이 쌓여도 결과를 모르는 주문은 남는지, 지운 주문을 다시 결제해도 새로 요청하는지 테스트함. 지우는 호출을 빼거나 unknown까지 지우게 바꾸면 각각 해당 테스트가 실패하는 것을 확인함
- 솔직한 결과: 300건 측정에서는 이 수정의 메모리 차이가 보이지 않음(상태 객체가 작아서). 그래도 상한이 없는 구조라서 막음

## 5. Sentry 지연 로딩은 하지 않기로 함

- 지난 회고에서 Sentry가 주문 번들을 gzip 96KB에서 127KB로 키운 것을 측정만 하고 판단을 미뤘음
- 확인: Sentry 초기화를 뺀 빌드와 비교함. 각 15회 중앙값

| 6배 스로틀 | Sentry 있음 | Sentry 없음 | 차이   |
| ---------- | ----------- | ----------- | ------ |
| 첫 화면    | 75.2ms      | 67.6ms      | +7.6ms |
| 스크립트   | 41.8ms      | 36.8ms      | +5.0ms |

- 1배에서는 차이가 없음
- 결정: 동기로 둠. 지연 로딩으로 아끼는 건 저사양에서 첫 화면 약 8ms인데, React 루트 에러 훅이 동기로 필요해서 Sentry가 뜨기 전 에러를 담아 둘 큐를 따로 둬야 함. 초기화 직후에 나는 에러를 놓칠 위험과 그 큐의 복잡도가 8ms보다 크다고 봄. 번들이 커져서 이 차이가 커지면 다시 봄

## 6. 측정 창이 포커스를 가져가고, 가려지면 멈춤

- 이슈 1: 측정할 때마다 Electron 창이 떠서 작업하던 앱의 포커스를 가져감. macOS는 앱이 뜨는 순간 활성화됨
- 해결: `--measure`로 띄우면 시작 전에 `app.setActivationPolicy('accessory')`로 Dock에 없는 보조 앱으로 만들고, 창은 투명하게 `showInactive()`로 띄움. `show: false`로 숨기면 Chromium이 화면을 그리지 않아 측정이 틀어짐
- 이슈 2: 결제 뒤 결과 다이얼로그가 가끔 안 뜸. 같은 조건에서 8번 중 5번
- 원인 찾기: 앱 버그를 먼저 의심해서 결제 상태와 DOM 변화를 로그로 남김. 결제는 승인되고 장바구니도 비워지는데 다이얼로그만 없었음. overlay-kit은 오버레이를 마운트한 뒤 `requestAnimationFrame` 안에서 `OPEN`을 보내는데, 측정 창이 다른 창에 가려지면 Chromium이 rAF를 멈춤. 실제 포스처럼 창이 맨 앞에 있으면 생기지 않고, 창이 다시 보이면 열림
- 해결: 측정 중에만 `backgroundThrottling: false`와 가려진 창 백그라운드 처리를 끄는 스위치를 켬
- 배운 점: 재현이 들쭉날쭉하면 앱보다 측정 환경을 먼저 의심할 것. 이번에는 그 반대 순서로 봐서 시간이 더 걸렸음

## 남은 고민

- 6배 스로틀은 추정치임. 실제 단말기에서 같은 스크립트를 돌려 비율을 맞춰야 함
- 측정을 CI에 넣지는 않음. 번들 크기처럼 흔들림이 적은 값부터 기준을 두고, 시간 지표는 변경 이력과 함께 주기적으로 보는 게 맞다고 봄
- 결과를 모르는 동안 장바구니를 잠그는 작업(PR #10)과 같은 파일(`OrderPage.tsx`)을 고쳐서, 먼저 머지되는 쪽에 맞춰 다른 쪽을 다시 올려야 함
