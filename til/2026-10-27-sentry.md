# Sentry 연결 회고

웹뷰 번들에는 `@sentry/react`, Electron 셸에는 내장 `crashReporter`를 붙이고, 결제 SDK 플러그인으로 결과를 모르는 결제를 경고 이벤트로 보내게 한 작업.

## 한 줄 요약

모니터링에서 가장 위험한 실패는 조용히 꺼져 있는 것이다. DSN은 넣었는데 CSP가 막고 있으면 앱에는 아무 증상이 없다. 그래서 "보내지는가"를 실제 빌드와 가짜 수집 서버로 확인하고, 그 조건을 테스트로 고정했다.

## 1. Sentry를 어디에 어떤 SDK로 붙일까

- 고민: `@sentry/electron`을 쓰면 메인과 렌더러 이벤트를 IPC로 이어주고 설정도 한 번이면 됨
- 판단
  - 렌더러 쪽에서 `@sentry/electron/renderer`를 import해야 함. 이 레포의 번들은 실행 환경을 모른다는 원칙(브릿지 인터페이스만 앎)이 있고, 같은 번들이 브라우저에서도 돌아야 함
  - 셸에 런타임 의존성이 생기면 패키징 회고에서 정리한 "node_modules 없는 asar" 구조가 깨짐
- 결정: 번들은 브라우저용 `@sentry/react`. 셸은 의존성 없이 Electron `crashReporter`가 DSN에서 만든 minidump 주소로 네이티브 크래시만 보냄. JS 에러는 번들이, 프로세스 크래시는 셸이 맡도록 책임을 나눔
- 잃은 것: 메인 프로세스의 JS 예외는 수집하지 않음. 메인 코드는 IPC 연결과 창 관리뿐이라 지금은 감수함. 메인 로직이 커지면 다시 봄
- 배운 점: 도구가 주는 편의보다 구조의 원칙을 먼저 본다. 원칙을 깨는 편의는 나중에 비용으로 돌아온다

## 2. 번들이 Sentry를 직접 모르게 하기

- 결정: `packages/monitoring`에 초기화와 수집 정책을 두고, 번들은 `initMonitoring`, `rootErrorHandlers`, `monitor`만 씀. 번들에서 `@sentry/*`를 import하면 린트 에러
- 이유: 수집 정책(개인정보, 릴리스 이름, 태그)은 시재관리 번들의 `Providers`와 달리 모든 번들이 같이 바뀌어야 함. 셸 번들 전환 회고의 기준("함께 바뀌는가")을 그대로 적용함
- `monitor`는 `addBreadcrumb`, `captureMessage` 두 개만 감쌈. 결제 플러그인은 `Monitor` 인터페이스를 받아서, 테스트에서는 `vi.mock` 없이 가짜 객체를 넣음

## 3. Sentry 11에서 sendDefaultPii가 사라짐

- 이슈: `sendDefaultPii: false`를 넣었더니 타입 에러. 익숙한 옵션이었음
- 원인 찾기: 설치한 `@sentry/core` 11.9.0의 타입 정의를 직접 읽음. 수집 범위가 `dataCollection` 하나로 바뀌었고 범주별 기본값이 대부분 `true`였음
- 해결: `userInfo`, `cookies`, `httpHeaders`, `urlQueryParams`를 끄고 `httpBodies: []`. 결제 이벤트에는 주문 ID, 금액, 멱등 키만 직접 담음. 카드 정보는 SDK까지 오지 않음
- 재발 방지: 수집 범위를 테스트로 고정함. 버전을 올리며 기본값이 바뀌어도 이 레포가 보내는 범위는 테스트가 지킴
- 배운 점: 개인정보 기본값은 버전마다 바뀐다. 블로그나 기억보다 설치된 버전의 타입 정의가 정확하다. 타입 에러가 오히려 기본값 변화를 알려줬다

## 4. ErrorBoundary가 삼킨 에러

- 이슈: 그라운드 룰대로 화면 영역마다 `ErrorBoundary`를 둠. 경계가 잡은 에러는 대체 화면으로 바뀌고 `window.onerror`까지 올라가지 않아서 Sentry 전역 핸들러가 모름
- 선택지: 경계마다 `onError`를 붙이기, 또는 React 19의 `createRoot(container, { onCaughtError, onUncaughtError, onRecoverableError })`
- 결정: 루트 훅. 경계를 새로 만들 때 리포팅을 빠뜨릴 수 없음
- 타입 문제: React 훅의 `componentStack`은 `string | undefined`, Sentry `reactErrorHandler`가 받는 React `ErrorInfo`는 `string | null`. `exactOptionalPropertyTypes`에서 안 맞아서 `?? null`로 맞춰주는 어댑터를 둠
- 확인: 경계 안에서 던진 에러가 대체 화면으로 바뀌면서 루트 훅으로 보고되는지 jsdom 테스트로 확인함

## 5. CSP가 리포팅을 조용히 막음

- 가설: 셸 번들 전환 때 넣은 CSP가 `connect-src 'self'`라서 Sentry 전송이 막힐 것
- 확인: 로컬에 Sentry 수집 서버를 흉내 내는 HTTP 서버를 띄우고 `SENTRY_DSN=http://public@127.0.0.1:9876/1`로 빌드함. 빌드한 셸을 CDP로 조작해 렌더러에서 에러를 던짐
  - CSP에 DSN 출처를 넣었을 때: 수집 서버에 `POST /api/1/envelope/`로 `monitoring-check` 이벤트 도착
  - 일부러 넣지 않았을 때: 렌더러 콘솔에 `violates the following Content Security Policy directive`만 찍히고 수집 서버에는 아무것도 오지 않음. 화면은 멀쩡함
- 해결: `createBundleConfig`가 `SENTRY_DSN`을 읽어 출처(`new URL(dsn).origin`)만 `connect-src`에 추가함. `script-src`는 그대로 `'self'`
- 재발 방지: "DSN이 있으면 CSP에 그 출처가 있다"를 `createBundleConfig` 단위로 테스트함. CSP 플러그인의 Vite `api` 필드에 최종 정책을 노출해서 테스트가 읽게 함. 출처 추가를 지우면 이 테스트가 실패하는 것도 확인함
- 배운 점: 보안 정책과 관측 도구는 서로를 모른다. 둘을 같은 설정 함수에서 만들게 하면 한쪽만 바뀌는 일을 구조로 막을 수 있다

## 6. 네이티브 크래시도 같은 방식으로 확인

- `crashReporter`는 DSN을 `https://<host>/api/<project>/minidump/?sentry_key=<key>`로 바꿔 `submitURL`에 넣음. 변환은 순수 함수로 두고 테스트함. 키나 프로젝트가 빠진 DSN은 조용히 넘기지 않고 에러를 냄
- 설치한 앱은 실행할 때 환경 변수를 받지 않으므로 tsdown `define`으로 빌드 시점 DSN을 코드에 넣음. 빌드 결과에서 `startCrashReporting("https://...")`로 바뀐 것을 확인함
- 확인: 같은 가짜 수집 서버를 둔 채로 CDP로 렌더러를 `chrome://crash`로 보냄. `POST /api/1/minidump/`로 약 650KB의 `upload_file_minidump`가 도착함

## 7. CI 시크릿은 없으면 빈 문자열

- 이슈: 릴리스 워크플로에서 `SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}`처럼 넘기면, 시크릿을 등록하지 않은 저장소에서는 변수가 없는 게 아니라 빈 문자열이 됨. `env.X !== undefined`로만 보면 빈 토큰으로 소스맵 업로드를 시도함
- 해결: 빈 문자열도 없는 것으로 보는 `read()`를 두고 테스트함. 시크릿이 없으면 모니터링 없이 빌드됨
- 소스맵은 macOS 잡에서만 올림. 번들 결과물이 OS와 상관없이 같아서 두 번 올릴 이유가 없음. 올린 뒤에는 `.map`을 지우고 `sourcemap: 'hidden'`이라 결과물에 `sourceMappingURL`도 남지 않음

## 남은 고민

- 번들 크기: Sentry가 들어가면서 주문 번들이 305KB에서 397KB(gzip 96KB에서 127KB)로 커짐. DSN이 없는 빌드에도 SDK 코드가 들어감. 셸이 로컬 파일로 열어서 네트워크 비용은 없고 파싱 비용만 늚. DSN이 있을 때만 동적 import로 불러오는 방법이 있지만, 루트 에러 훅이 동기로 필요해서 초기 에러를 놓치지 않게 큐를 둬야 함. 측정해보고 정함
- 메인 프로세스 JS 예외: 지금은 수집하지 않음. 메인 로직이 커지면 crashReporter 외에 전송 경로가 필요함
- 실제 Sentry 프로젝트로는 확인하지 못함. 가짜 수집 서버로 경로, CSP, 형식까지만 봄. 실제 수집 서버의 CORS 응답은 저장소에 DSN을 등록한 뒤 릴리스 빌드에서 확인해야 함
