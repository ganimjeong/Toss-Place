# POS 첫 릴리스와 Sentry 릴리스 이름 회고

`pos@0.1.0` 태그로 macOS, Windows 설치 파일을 처음 릴리스함. 릴리스는 성공했는데 로그를 읽어 보니 Sentry 소스맵 업로드가 실패해 있었음.

## 한 줄 요약

워크플로가 초록색이어도 모니터링은 꺼져 있을 수 있다. Sentry 연결 회고에서 "가장 위험한 실패는 조용히 꺼져 있는 것"이라고 써 놓고, 같은 종류의 실패를 업로드 단계에서 다시 만났다.

## 1. 성공한 빌드 안에 숨은 400

- 이슈: 릴리스 워크플로의 모든 잡이 성공했고 dmg, exe도 올라감. 그런데 macOS 잡 로그에 `[sentry-vite-plugin] Failed to create release: 400 Bad Request`가 번들마다 찍혀 있었음
- 확인 계기: 시크릿을 처음 넣고 돈 빌드라, 성공 여부와 별개로 Sentry 관련 로그만 따로 뽑아 봄. 이 확인을 안 했다면 소스맵 없는 앱이 배포된 걸 실제 크래시가 났을 때 알았을 것
- 원인 찾기
  - 401이면 토큰, 404면 조직이나 프로젝트 slug 문제인데 400은 요청 내용 문제
  - 요청에 들어가는 값 중 우리가 만든 건 릴리스 이름뿐. `${name}@${version}`이라 `@toss-place/order@0.0.0`이 됨
  - Sentry 문서의 릴리스 이름 규칙: 줄바꿈, 탭, `/`, `\`를 쓸 수 없음. scope 구분자 `/`가 걸림
- 해결: `toReleaseName`이 앞의 `@`를 빼고 `/`를 `-`로 바꿈. `toss-place-order@0.0.0`. 업로드와 번들 초기화가 같은 값을 쓰므로 이 함수 하나만 고치면 둘이 같이 바뀜

## 2. 업로드 실패가 빌드를 멈추지 않은 이유

- 이슈: 플러그인 타입 주석에는 "errorHandler가 없으면 에러를 던져 번들링을 멈춘다"고 돼 있는데 빌드는 통과함
- 원인: 설치된 `@sentry/bundler-plugins` 11.9.0 코드를 읽어 보니 `handleRecoverableError(e, throwByDefault)`의 두 번째 인자가 옵션 검증 실패 같은 일부 경우만 `true`이고, 릴리스 생성과 소스맵 업로드는 `false`라 로그만 남김. 주석과 실제 동작이 달랐음
- 해결: `errorHandler`에서 에러를 다시 던짐
- 판단 기준: 설정이 없으면 플러그인을 아예 빼고 모니터링 없이 빌드함(포크 저장소, 로컬 빌드). 설정이 있는데 실패하면 빌드를 멈춤. "설정 없음"과 "설정했는데 실패"를 구분한 것. 배포 설정 회고에서 SDK 토큰과 Sentry 시크릿을 다르게 다룬 기준과 같음
- 대가: Sentry 장애 때 릴리스도 멈춤. 태그 워크플로를 다시 돌리면 되고, 소스맵 없는 앱을 매장에 까는 것보다 낫다고 봄
- 확인: 가짜 토큰으로 `bundles/order`를 빌드해서 `401 Unauthorized`로 빌드가 실패(종료 코드 1)하는 것을 봄. 고치기 전 같은 상황이면 통과했을 것

## 3. 남은 고민: 번들 버전이 0.0.0에 고정됨

- 릴리스 이름이 번들의 `package.json` 버전을 쓰는데, 번들은 셸과 따로 버전을 올리지 않아서 항상 `0.0.0`임. POS `0.1.0`과 `0.2.0`의 에러가 같은 Sentry 릴리스로 묶임
- 소스맵 연결 자체는 플러그인이 넣는 debug ID로 파일 단위로 이어져서 깨지지 않음. 문제는 "어느 버전에서 늘었나"를 볼 수 없다는 것
- 후보: 릴리스 이름에 셸 버전(POS 버전)을 넣거나, 번들별 버전을 Changesets로 관리함. 번들을 셸과 따로 배포하는 구조가 아직 없어서 전자가 맞아 보임. 다음 POS 릴리스 전에 정함

## 확인

- `@toss-place/vite-config` 테스트, 타입, 린트 통과
- 가짜 토큰 빌드가 실패하는 것 확인
- PR #15의 Release POS 패키징에서 `Successfully uploaded source maps to Sentry`가 번들 두 개 모두 찍힘. Sentry 릴리스 화면에 `toss-place-order`, `toss-place-cash`가 생긴 것도 확인함. 둘 다 버전이 `0.0.0`이라 3번 고민이 화면에서도 그대로 보임
- `pos@0.1.0` 설치 파일은 고치기 전 이름으로 빌드돼 번들의 릴리스 값도 `/`가 든 이름임. 셸을 `0.1.1`로 올려 다시 릴리스함
