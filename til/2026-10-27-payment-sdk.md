# 결제 SDK 회고

주문 번들 안의 `useCardPayment` 훅을 `@toss-place/payment-sdk` 패키지로 꺼낸 작업. 결제 상태 전이, 중복 요청 방지, 결과를 모르는 결제의 조회와 복구를 SDK가 맡고, 번들은 React Query로 화면 상태만 연결함.

## 한 줄 요약

결제 실패는 "안 나갔다"와 "나갔는지 모른다" 두 가지다. 둘을 같은 `ok: false`로 다루던 구조가 이중 결제의 원인이었고, SDK는 이 둘을 타입과 상태로 갈라놓는 일을 한다.

## 1. 멱등 키를 useRef에 두면 화면과 같이 사라짐

- 이슈: 기존 훅은 멱등 키를 `useRef`에 두고 승인되면 지웠음. 버튼 연타는 막지만, 결제 중에 셸 메뉴로 시재관리(`Cmd+2`)로 넘어가면 주문 웹뷰가 통째로 내려가면서 키도 사라짐. 셸의 단말기는 메인 프로세스에서 계속 돌아서 승인은 남음. 돌아온 사장님은 결제 결과를 못 봤으니 다시 결제를 누르고, 새 키로 두 번째 승인이 나감
- 원인 찾기: 멱등 키의 수명이 "결제 시도"가 아니라 "컴포넌트"에 묶여 있었음. 번들 구조에서는 웹뷰가 언제든 내려갈 수 있어서 렌더러 메모리에 둔 값은 결제 하나를 끝까지 지키지 못함
- 해결: 단말기에 요청을 보내기 전에 시도(주문 ID, 금액, 멱등 키)를 저널에 먼저 쓰고(write-ahead), 결과가 확정된 뒤에 지움. 앱을 열 때 `recover()`가 저널에 남은 시도를 멱등 키로 조회함. 지우는 순서도 "결과 확정 → 저널 삭제"로 고정함. 반대면 그 사이에 꺼졌을 때 기록이 사라짐
- 확인: 빌드한 Electron 셸을 띄우고 CDP로 결제 버튼을 누른 직후 시재관리로 이동, 돌아와서 "화면이 닫히기 전에 승인된 결제가 있어요. 8,500원" 안내가 뜨고 저널이 비는 것까지 봄
- 재발 방지: 셸 단말기 stub에 카드 승인 지연(3초)을 넣어서 이 상황을 언제든 손으로 재현할 수 있게 함. 기존 stub은 즉시 승인하고 멱등 키도 무시해서 이 버그가 드러날 수 없는 구조였음
- 배운 점: 상태의 수명은 그 상태가 지켜야 하는 것의 수명에 맞춘다. 결제 시도는 화면보다 오래 산다

## 2. 실패를 둘로 나누기: 확정 실패와 결과 모름

- 고민: 기존 훅은 실패하면 키를 유지했음. TIMEOUT 뒤에 같은 키로 다시 보내는 건 안전하지만, DECLINED 뒤에 다른 카드로 다시 결제할 때도 같은 키가 나감. 멱등 키를 지키는 PG라면 두 번째 요청에 첫 번째의 거절 응답을 그대로 돌려줌. 반대로 매번 새 키를 쓰면 TIMEOUT 뒤에 이중 결제가 남
- 판단: 사유마다 "돈이 나갔는지"에 대한 답이 다름. DECLINED, CANCELED는 결제되지 않았음이 확실하고, TIMEOUT, DISCONNECTED, IPC 예외는 단말기까지 요청이 갔는지 모름. 토스페이먼츠 문서도 에러 뒤에 키를 바꿔 재시도하는 건 위험하다고 하고, Adyen POS 가이드는 타임아웃 뒤 거래 상태 조회를 보내라고 함 ([research/07](../research/07-payment-reliability.md))
- 결정
  - `PaymentOutcome`을 `approved | failed | unknown`으로 둠. `unknown`은 실패가 아니라서 화면에서도 "다시 결제해 주세요"를 띄우지 않음
  - 결과를 모르면 결제 요청이 아니라 조회를 자동으로 반복함. 조회는 읽기라 몇 번을 해도 돈이 나가지 않음. 조회 결과에 `processing`을 따로 둬서, 손님이 아직 카드를 대는 중이면 `not-found`로 성급하게 확정하지 않음
  - 어떤 사유가 모호한지는 SDK가 아니라 번들이 `isAmbiguous`로 정함. 단말기마다 사유 코드가 다르고 SDK는 그걸 몰라야 함
- 배운 점: 재시도 정책은 "몇 번 할까"보다 "무엇을 다시 해도 안전한가"가 먼저다. 쓰기는 사람이 결정하고, 읽기는 기계가 반복한다

## 3. 상태 머신을 표로 두고 순수 함수로 만든 이유

- 고민: 상태별로 허용 이벤트를 타입으로 강제할지(상태마다 다른 메서드를 노출하는 방식), 런타임에서 막을지
- 판단: 결제 상태는 비동기 응답, 저널 복구처럼 바깥에서 들어오는 값으로 바뀜. 컴파일 시점에 상태를 알 수 없는 경로가 대부분이라 타입만으로는 못 막음
- 결정: `TRANSITIONS`를 `as const satisfies Record<PaymentStatus, readonly PaymentEventType[]>`로 둠. 상태가 늘면 표에서 빠진 키를 컴파일러가 알려주고, 표 자체가 문서가 됨. 전이는 `transition(state, event)` 순수 함수로 만들고 허용되지 않은 전이는 `InvalidTransitionError`를 던짐
- 순수 함수라서 얻은 것: 아래 4번 버그를 고칠 때 상태를 바꾸지 않고 "이 전이가 가능한가"만 미리 물어볼 수 있었음

## 4. 테스트가 처음부터 다 통과함

- 이슈: SDK 테스트 24개가 첫 실행에 전부 통과함. 지난 초기 세팅 때 "통과는 검사가 돌았다는 증거가 아니다"를 겪어서 의심함
- 원인 찾기: 핵심 보장을 하나씩 일부러 깨고 테스트가 잡는지 확인함(손으로 하는 mutation testing)
  - single-flight 제거 → 연타 테스트 실패
  - 이전 시도 조회 생략 → 복구 테스트 실패
  - 모호한 실패를 확정 실패로 → 4개 실패
  - "이전 시도가 아직 unknown이어도 새 결제 허용" → 전부 통과. 테스트가 없었음
- 더 보니 실제 버그도 있었음. 상태 머신이 `unknown`에서 `REQUEST`를 막긴 하지만, 그 검사보다 `journal.save(newAttempt)`가 먼저 실행돼서 결과를 모르는 이전 시도의 멱등 키를 새 키로 덮어씀. 예외는 나지만 이전 결제를 조회할 단서가 사라짐
- 해결: 저널에 쓰기 전에 `transition(getState(orderId), requestEvent)`로 전이 가능 여부를 먼저 확인함. "다시 눌러도 여전히 확인할 수 없으면 새로 요청하지 않고 이전 시도의 키를 지킨다"는 테스트를 추가하고, 같은 변이를 다시 넣어 실패하는지 확인함
- 배운 점: 테스트가 지키는 건 내가 떠올린 시나리오뿐이다. 보장 목록을 먼저 적고 하나씩 깨보면 빠진 시나리오가 보인다. 부수 효과(저널 쓰기)와 검증(전이)의 순서는 코드 리뷰로는 잘 안 보이는 종류의 버그였다

## 5. SDK와 React Query의 경계

- 결정: SDK는 React를 모름. 같은 SDK를 Electron 메인 프로세스나 다른 프레임워크에서도 쓸 수 있어야 해서임
- 번들 쪽
  - 결제는 `useMutation`. 중복 요청 방지와 멱등 키는 SDK가 하므로 mutation은 `isPending`을 화면에 연결하는 일만 함. 실패도 결과 객체로 오기 때문에 mutation이 reject되는 건 저널을 못 썼을 때뿐이고, 그때는 결제 요청이 나가지 않았다는 문구를 띄움
  - 복구는 `useSuspenseQuery`. 그라운드 룰대로 `isLoading` 분기 없이 쓰되, 메뉴 영역과 다른 `Suspense` 경계에 둠. 단말기가 끊겨 있으면 조회 재시도로 몇 초가 걸리는데, 그 때문에 주문 화면 전체가 기다리면 안 됨
  - 복구 안내는 늦게 나타나므로 레이아웃 안에 넣지 않고 화면 위에 띄움. 나타날 때 메뉴가 밀리지 않게 함
- 배운 점: Suspense 경계는 "무엇을 같이 기다려야 하는가"로 나눈다. 복구는 주문과 같이 기다릴 이유가 없다

## 6. npm 패키지로 내보내기: 워크스페이스는 src, 배포는 dist

- 고민: 다른 패키지는 `exports`로 `.ts` 소스를 바로 내보내서 빌드 없이 씀. SDK도 워크스페이스 안에서는 그대로 쓰고 싶지만 npm에는 JS와 타입 선언이 올라가야 함
- 결정
  - `exports`는 `./src/index.ts`, `publishConfig.exports`는 `dist`로 둠. `yarn pack`이 `publishConfig`를 반영하는지 tarball 안의 `package.json`을 열어 확인함
  - tsdown으로 ESM과 CJS를 같이 냄. 이 레포의 Electron 셸이 CJS로 빌드되는 것처럼, 결제 SDK를 쓸 곳이 ESM이라는 보장이 없음
  - `exports` 조건마다 `types`를 `default`보다 먼저 두고 `.d.ts`, `.d.cts`를 나눔. arethetypeswrong(`attw`)과 publint를 `check:package`로 묶어 CI에서 돌림
  - 배포는 `payment-sdk@x.y.z` 태그로만 함. 태그와 `package.json` 버전이 다르면 막고, `npm publish --provenance`로 어떤 커밋에서 빌드됐는지 서명을 남김
- 배운 점: 라이브러리의 진짜 공개 API는 소스가 아니라 tarball이다. 검사도 tarball을 대상으로 해야 한다

## 7. 플러그인은 관찰만 함

- 결정: 플러그인 훅은 `onStateChange(previous, next)` 하나만 둠. 결제 흐름을 바꾸는 훅(요청 가로채기 등)은 두지 않음
- 이유: 결제 SDK에서 확장 지점이 흐름을 바꿀 수 있으면, 플러그인 하나의 버그가 결제 실패가 됨. 플러그인이 던지거나 reject해도 `onPluginError`로만 보내고 결제 결과는 그대로 둠. 이걸 테스트로 고정함
- 다음 작업: Sentry 연결을 이 플러그인으로 붙임. `unknown`으로 끝난 결제는 사람이 확인해야 하는 사건이라 에러 리포팅 대상으로 봄

## 재발 방지 장치

- 번들에서 `requestCardPayment`를 직접 부르면 린트 에러(`no-restricted-syntax`). 결제 클라이언트 파일만 예외. 규칙이 실제로 걸리는지 일부러 위반하는 파일로 확인함
- `toPaymentMessage`의 문구 표를 `Record<PaymentFailureReason<CardPaymentFailureReason>, string>`으로 둠. SDK가 사유(`TRANSPORT_ERROR`, `INTERRUPTED`)를 추가하면 문구를 빠뜨린 곳에서 컴파일이 깨짐

## 남은 고민

- 금액이 바뀐 재시도: 결과를 모르는 결제가 있는 상태에서 메뉴를 더 담고 다시 누르면, 이전 시도가 이전 금액으로 승인된 것으로 확인될 수 있음. 지금은 승인 금액으로 영수증을 만들지만 품목은 현재 장바구니라 맞지 않음. 결제 결과를 모르는 동안 장바구니를 잠그는 쪽이 맞다고 봄
- 늦게 도착한 요청: `not-found`로 확정하고 새 키로 결제한 뒤에 원래 요청이 단말기에 늦게 도착하면 두 번 승인될 수 있음. 실제 단말기에서는 확정 전에 그 키로 망취소를 보내야 함
- 저널 위치: localStorage는 렌더러 저장소라 사용자 데이터 정리나 다른 출처(origin)에서는 못 읽음. 결제 기록은 셸 프로세스가 가진 저장소로 옮기고 브릿지로 읽는 게 맞음. 저널 인터페이스를 비동기로 둔 이유임
