# 결제 결과를 확인하기 전 장바구니 잠그기 회고

결제 중이거나 결제 결과를 모르는 동안 주문 화면의 메뉴 추가와 빼기를 막은 작업.

## 한 줄 요약

결제 SDK는 "돈이 두 번 나가는 것"을 막았지만 "돈은 한 번 나갔는데 주문이 바뀌는 것"은 막지 못했다. 결제 시도와 장바구니가 같은 것을 가리킨다는 보장은 SDK가 아니라 화면이 지켜야 했다.

## 왜 이걸 다음 작업으로 골랐나

후보는 셋이었음. 결제 SDK 회고의 남은 고민 세 개.

| 후보                                      | 생기는 일                                                       | 지금 고칠 수 있나                               |
| ----------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------- |
| 결과를 모르는 동안 장바구니가 바뀜        | 승인 금액과 영수증 품목이 어긋남. 더 담은 메뉴는 결제 없이 나감 | 화면에서 바로 고칠 수 있음                      |
| `not-found` 확정 뒤 늦게 도착한 원래 요청 | 두 번 승인될 수 있음                                            | 실제 단말기의 망취소 규격이 있어야 함           |
| 저널이 렌더러 localStorage에 있음         | 저장소를 지우면 기록이 사라짐                                   | 셸 저장소와 브릿지 API가 필요함. 구조 변경이 큼 |

- 첫 번째는 돈이 맞지 않는 문제라 이중 결제와 무게가 같음. 매장에서는 "영수증에는 두 잔인데 카드는 한 잔"으로 나타나고, 사장님은 이유를 알 수 없음
- 두 번째는 실제 단말기 없이는 검증할 수 없는 설계라, 지금 하면 추측으로 코드를 쓰게 됨
- 세 번째는 맞는 방향이지만 지금 저널이 사라지는 경로(저장소 수동 삭제)는 흔하지 않음
- 그래서 영향이 크고, 지금 레포 안에서 끝까지 검증할 수 있는 첫 번째를 고름. 회고에서 정한 기준("고쳤으면 그 환경에서 돌려보고 쓴다")을 지킬 수 있는 작업이기도 했음

## 1. 먼저 버그를 재현함

- 시나리오
  1. 단말기는 승인했지만 응답이 오지 않음
  2. 조회도 연결이 끊겨 실패해서 결과를 모름 상태가 됨
  3. 그 사이에 아메리카노를 하나 더 담음
  4. 단말기가 다시 연결되고, 결제 버튼을 다시 누름
- 결과: SDK는 설계대로 새로 결제하지 않고 이전 시도(4,500원)를 승인으로 확인함. 화면은 승인됐으니 현재 장바구니(아메리카노 2잔, 9,000원)로 영수증을 만들고 장바구니를 비움. 테스트는 `expected 9000 to be 4500`로 실패함
- 판단: SDK의 결제 시도와 화면의 장바구니가 서로 다른 시점의 주문을 가리키게 된 것. SDK는 장바구니를 모르니 SDK 버그가 아님. "결제 시도가 살아 있는 동안 그 주문은 바뀌지 않는다"는 불변식을 화면이 지키지 않았던 것
- 재현 테스트는 수정 전에 실패하고 수정 후에 통과하는 형태로 남김. 메뉴 버튼 이름을 `/아메리카노/`로 찾다가 장바구니의 "아메리카노 하나 빼기" 버튼까지 잡혀서 `/^아메리카노\s*4,500원$/`로 좁힘

## 2. 무엇을 잠글까

- 잠그는 때: 결과를 모를 때만이 아니라 결제 중일 때도 잠금. 셸 단말기는 승인에 3초가 걸리고, 그 사이 메뉴를 담으면 같은 문제가 생김
- 잠그는 것: 메뉴 추가와 빼기. 결제 버튼은 결과를 모를 때 "결제 결과 확인"으로 바꿈. 누르면 새 결제가 아니라 이전 시도부터 조회한다는 걸 문구로 드러냄
- 상태 표현: 장바구니 패널은 `isPaying`, `isAwaitingConfirmation` 두 boolean 대신 `'idle' | 'paying' | 'awaiting-confirmation'` 하나를 받음. 두 boolean이면 "결제 중이면서 확인 대기" 같은 있을 수 없는 조합이 타입상 생김. 버튼 문구도 `Record<CartPaymentStatus, string>`라 상태가 늘면 문구를 빠뜨린 곳이 컴파일에서 드러남
- 잠금의 기준은 주문 ID로 묶음. 마지막 결제 결과가 `unknown`이고 그 시도의 주문 ID가 지금 주문과 같을 때만 잠금. 새 주문을 시작하면 이전 주문의 결과에 끌려가지 않음

## 3. 잠금에서 나가는 길

- 고민: 단말기가 계속 죽어 있으면 잠금이 영원히 풀리지 않음. 실제로는 앱을 다시 켜면 장바구니가 사라지니 빠져나갈 수는 있지만, 사장님이 그 방법을 알 수 없음
- 결정: "새 주문으로 넘기기" 버튼을 두고 확인 다이얼로그를 거치게 함. 장바구니를 비우고 새 주문 ID를 만듦
- 지키는 것: 이전 시도는 저널에서 지우지 않음. 다음 실행 때 다시 조회되고, 결과를 모른다는 경고는 Sentry로 이미 감. 화면에서 넘어가도 돈의 흔적은 남김. 이 부분을 테스트에서 저널 내용으로 확인함
- 하지 않은 것: "단말기에서 확인했어요, 결제 안 됐음"처럼 사람이 결과를 확정하는 버튼은 두지 않음. 사람의 판단으로 저널을 지우는 건 이중 결제를 막는 마지막 근거를 지우는 일이라, 단말기 승인 내역을 대조하는 기능과 같이 설계해야 함

## 4. 확인

- 잠금을 하나씩 일부러 풀어서 테스트가 잡는지 봄
  - 메뉴 잠금 제거 → 결제 중 테스트, 재현 테스트 실패
  - 빼기 잠금 제거 → 결제 중 테스트 실패
  - 확인 대기 상태 무시 → 재현 테스트, 새 주문 테스트 실패
- 빌드한 셸에서 결제 버튼을 누른 직후 화면을 캡처해서, 메뉴와 빼기 버튼이 비활성화되고 결제 버튼이 "결제 중"으로 바뀐 것을 봄
- 결과를 모르는 상태를 기다리는 테스트는 조회 재시도(최대 약 7.5초)를 실제로 기다리지 않게 `vi.useFakeTimers({ shouldAdvanceTime: true })`로 시간을 넘김. `shouldAdvanceTime` 없이 돌려보니 Testing Library의 `findBy` 대기까지 멈춰서 15초 시간 초과로 실패함. 가짜 타이머와 `findBy`를 같이 쓰려면 이 옵션이 필요함

## 배운 점

- 불변식이 어느 계층의 것인지 먼저 정한다. 멱등 키와 저널은 SDK의 불변식이고, "결제 시도와 장바구니가 같은 주문"은 화면의 불변식이다. SDK를 잘 만들어도 화면의 불변식은 화면이 지켜야 한다
- 잠금을 넣을 때는 나가는 길을 같이 설계한다. 나가는 길이 무엇을 지우고 무엇을 남기는지가 잠금 자체보다 중요하다

## 남은 고민

- "새 주문으로 넘기기"로 남겨둔 시도는 지금 실행 중에는 다시 조회하지 않고 다음 실행 때 조회함. 단말기가 다시 연결되면 바로 조회하도록 브릿지에 연결 상태 이벤트가 필요함
- 사람이 결과를 확정하는 흐름은 단말기 승인 내역 조회와 함께 설계해야 함
